# キャラ・アクション追加時の検査

## 2026-10-08の見落としと対策

静止したコマの矩形検査だけで「修正済み」と判断したため、実際のデモ中に起きる欠けを見落とした。以後は下記を公開前の合格条件にする。自動検査だけで目視確認済みとは記録しない。

| 原因 | 実装と検査 |
| --- | --- |
| 画像URLを変えずにアトラスを更新し、24時間キャッシュされた旧画像と新しいコマ位置が混在。鎖鎌旋回時に身体が消える | ビルド時に画像のSHA-256をURLへ付け、同じ内容の画像だけキャッシュする。`tkusarivisibility.js`で旧画像が残るブラウザを再現し、全6人の停止・移動中の旋回を左右・両画質で毎フレーム検査する。 |
| 武器を含む矩形の中心で位置を合わせると、武器を振るたびに胴体がずれる | 接地する足を原点にし、アニメーションごとの一定倍率で体格を合わせる。意図した跳躍は保持する。`boss_registration.py`と接地テストで確認する。 |
| 画面端の制限が身体幅しか考慮せず、弓・槍や後退中の攻撃が欠ける | 全攻撃コマ・両向きの最大幅から固定余白を求める。入場完了前は攻撃させない。左右入場・後退・突進・ワープを検査する。 |
| 攻撃の挙動タグだけで絵を選び、三連射や回転斬りに違うシートが出る | 既定と異なる技は`anim`を明示し、その技が期待する配列を選ぶこともテストする。 |
| 地上では収まる弓が、上側レーンの跳躍頂点では欠ける | 最も背が高いコマと武器を含めて跳躍速度を制限する。上・中央・下レーン、左右向きで実際の技を最後まで動かす。 |
| 武器系統の代表絵にまとめ、斧・棍棒が長剣に見える | 馬上も拾得武器9種類を別配列で登録し、所持武器に対応する行を描画したことを検査する。武器アイコンを使う描画から一体コマを採取し、元PNGは保持する。 |
| 攻撃段数が増えて素手側の対応が欠け、武蔵5段目で元の二刀に戻る | 通常の全段と全拾得武器で、素手素体＋所持武器を描画したことを検査する。 |
| 絵が弓・銃でも、馬上の攻撃処理は近接のまま | 発射物の種類・左右方向・地上の敵への命中・使用回数消費を別テストにする。 |

## 追加・変更の手順

1. 原画PNGは削除・上書きせず、必要なら新バージョンを追加する。指定寸法、純マゼンタ、装備の連続性、隣コマの混入、OCR、GIF復号と動作目視を素材台帳で確認する。
2. 待機→歩き→攻撃→待機を見て、顔・鎧・旗・体格・接地位置が連続しているか確認する。武器の先端だけで体格を合わせない。
3. ボスの技は`TY`に登録してから、下記テストを実行する。新ボスも`tbosstechniques.js`の対象へ自動的に入る。アトラスのキーが異なる場合はテスト側にも対応を追加する。
4. Android相当の横画面で自動デモAIを動かし、各ボスの攻撃中のゲーム画面を保存して目視する。シートの一覧画像だけでは合格にしない。検査用にHPや出現波を変更した場合は、自然な全編通しと区別して記録する。
   デモの速度を×0.25にして、怪しい瞬間は停止→1コマで前後を確認する。`tdemoslowcapture.js`は8ボスの対戦を準備し、実際のAIが選んだ攻撃の有効時間を撮影する。guard/stepは攻撃として数えない。敵の無敵時間を極端に増やすとAIが攻撃を開始しないため、撮影用の耐久強化にはHPを使う。
5. 数値検査・動作画像・実施環境・未確認範囲を記録し、通過したコミットだけをpush・デプロイする。

主人公6人も公開前の対象に含める。検査表の軸は「キャラ×本来の武器・拾得武器×徒歩・馬上×攻撃の種類×左右向き×上中下レーン」。通常連続技、突進、ジャンプ、溜め、必殺を確認する。馬上は専用の一体絵を使い、武器系統とシートの対応、地上の敵へ向く打点を目視する。鎖鎌は回転中の移動、投擲、引き寄せ、斬撃、回収も別に確認する。絵の選択が正しくても、当たり判定・射程・発射方向まで正しいとは限らないので区別する。

`tbosstechniques.js`はChromeとPlaywrightを使用する。ローカルサーバーを先に起動し、`OUT`環境変数で画像・JSONの保存先を指定できる。実際の全技を左右向き・3レーンで進め、毎フレームの描画矩形を検査する。全編進行、Android実機、全端末の低画質モードまで保証する検査ではない。
